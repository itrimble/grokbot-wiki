Project tracking: design and baseline

Project tracking: design and baseline

Owner: Archivist. Built 2026-10-19 after the SnapDog Creator Studio miss: work built Oct 17-18 on the MacBook Pro was only found Oct 19 when Scout asked, because the docs refresh ran once a day at 06:00 CT and no scan of ~/projects existed. This page is the design for proactive tracking. Scanner + manifests live on the box in /workspace/project-tracker/ (not in this repo; manifests are machine output, this page is the record).

Canonical root and replicas (settled 2026-10-19)

  • Canonical: AIMacMini:~/projects. Marker file ~/projects/.canonical exists on the mini (verified 2026-10-19, empty file dated Oct 6). Per Ian via Beacon (2026-10-19): writing to mini ~/projects replicates automatically to the other machines and the NAS. So the mini manifest is the truth; MBP, Neo and NAS manifests are replica / lag checks only. Divergence from the mini is reported as sync lag, not as separate work, unless a replica is ahead (dirty files or folders the mini does not have yet).
  • NAS edits are allowed (decision 2026-10-16), but the NAS is a replica target, not the canonical root.
  • omarchy is excluded from scanning (offline, faulty RAM).

Access paths (no addresses recorded here)

  1. First test is ssh mini from the box (SSH alias in ~/.ssh/config, SOCKS proxy) and/or a tailscale ping. ListMachines showing "disconnected" is not evidence the mini is down — on 2026-10-19 it showed disconnected while ssh mini worked and Beacon verified the mini by tailscale ping (DERP). The box had also lost ssh/nc in a morning restart (since reinstalled), so test the tools, not the list.
  2. Fallback: from the MBP over LAN SSH, ssh ian@[redacted LAN host] (verified 2026-10-19: mini ~/projects present, snapdog HEAD 797b61c matched the MBP).
  3. Fallback 2 (verified 2026-10-19 17:07 CT): from the Neo over LAN SSH, ssh neo 'ssh ian@[redacted LAN host] ...'. At 17:07 CT the box's SOCKS route failed for mini and mbp (SOCKS general failure) while neo worked, and the mini scan ran fine through the Neo hop.
  4. If all fail: mark the mini unverified in that run's diff, scan a replica (MBP first), and say plainly that the canonical state is unchecked. Never report the mini as down from ListMachines alone.

The scanner

/workspace/project-tracker/scan_projects.py (stdlib only, Python 3). It runs on each machine (piped over SSH stdin, so nothing has to be installed or left behind) and prints one JSON manifest to stdout:

ssh mini 'python3 - scan ~/projects --label mini-projects' < scan_projects.py > manifests/YYYY-MM-DD-mini-projects.json
ssh mbp  'python3 - scan /Volumes/nas/projects --label nas-projects --inventory-only' < scan_projects.py > manifests/YYYY-MM-DD-nas-projects.json   # NAS via MBP mount; git over SMB is too slow (see below)
python3 scan_projects.py scan ~/projects --label local-projects            # or locally on any machine
python3 scan_projects.py scan ~/projects --label mini-projects --skip-dirty  # fast intraday mode: no git status
python3 scan_projects.py scan /Volumes/nas/projects --label nas-projects --inventory-only  # NAS/SMB: names+mtime only, no git
python3 scan_projects.py diff manifests/OLD.json manifests/NEW.json --out LATEST-DIFF.md
python3 scan_projects.py diff manifests/OLD.json manifests/NEW.json --format json

Per top-level folder/file the manifest records: name/relative path, folder mtime, is_git, branch, HEAD, dirty file count (git status --porcelain line count), remote names only (never URLs — a URL can carry a token), last commit (hash/date/subject), the last 25 commits (so a diff can name the new commit subjects), and nested_git: git repos found up to 2 levels below the folder.

Rules the scanner follows:

  • Read-only git only: rev-parse, branch, status, log, remote (names). No file contents are read, no code is opened, nothing in any project repo is changed.
  • A per-repo timeout keeps one hung repo from stalling the scan; a repo whose status fails is recorded with dirty_count: null + an error, not silently dropped.
  • Limitation (v1): branch/HEAD/dirty are collected for top-level repos only. Nested repos are named, not tracked — on the mini, 40 nested .git dirs were found (including vendored checkouts and _handoffs/ copies). Real projects hide there (Pipe Flow/PlumberPuzzle, books/*, astralforge/AstralForge-iOS, quickstart/zoom-recording-downloader). v2 should promote nested repos that are not under .build/, _handoffs/, external_repos/ or a parent git repo's vendored deps to full entries.

Diff mode

Manifests are keyed by relative name, so any two roots/dates compare. A diff reports: new entries, removed entries, branch changes, HEAD changes with the new commit subjects (commits in the new manifest's 25-commit window that were not in the old one), dirty-count changes, and repos that became git / stopped being git. The same command does yesterday-vs-today (what changed) and mini-vs-MBP (replication lag).

Standing rule: every projects folder gets a commit (Ian, 2026-10-19)

Ian's words 2026-10-19 14:16 CT: 'Going forward if a projects folder doesn't have a commit it should.' And on ~/projects/neo: 'It was to add the neo to the build orchestration stack so that the Mac mini and mbp would [not] always be bogged down.'

  • Every folder in ~/projects should be a git repo with at least an initial commit. A non-git folder is a tracking gap to promote/flag, not just an mtime line.
  • Remediation approach: the daily (Tier 2) scan lists non-git folders touched in the last 7 days and maintains a standing backlog list of all non-git top-level folders. Baseline 2026-10-19: 120 non-git top-level dirs on the canonical mini (of 200 top-level entries; 74 git repos). Those ~120 are not all necessarily projects — they include non-project/data/scratch dirs — so flag them for Ian / git-init case-by-case rather than auto-init en masse.
  • Do not git-init folders en masse without Ian's per-folder or batch yes. ~/projects/neo was git-initialised 2026-10-19 under this rule (initial commit 5bfa987, main, no remote); no other folder was initialised in that pass.
  • Fix already noted above for the non-git blind spot stays: daily scan must promote any non-git folder touched in the last 7 days with no OPEN-WORK item.

Cadence proposal

Two tiers, so Archivist notices within hours without drowning Ian in noise. Neither tier is live yet — turning either on as a scheduled routine needs Ian's yes.

Tier 1: intraday HEAD-only check-ins (cheap, quiet)

  • When: 09:00, 13:00, 17:00, 21:00 CT daily.
  • What: scan --skip-dirty on the mini only; diff against the last manifest (intraday or daily). A full mini scan took under ~2 minutes from the box in the baseline; HEAD-only is faster because it skips git status on huge dirty trees.
  • Surfaces only: new top-level folder, new branch or branch change, HEAD change in a repo with no matching OPEN-WORK item, or a HEAD change on a non-main feature branch (the SnapDog signal: claude/snapdog-swiftui-app-g6bvt moving on a weekend).
  • Everything else is written to the day's manifest silently. No message to Ian unless an untracked repo moves — that is the whole point.

Tier 2: daily deep diff (before the 06:00 CT docs refresh)

  • When: ~05:30 CT daily, feeding the existing daily docs refresh.
  • What: full scan (with dirty counts) on the mini; full diff vs yesterday's deep manifest; replica lag check (MBP + Neo, HEAD-only) twice a week; NAS inventory-only lag check weekly (see cost note).
  • What gets recorded:
    • OPEN-WORK.md: a new item only when an active repo (commit in the last 7 days) has no tracked item under any name, or a tracked repo ships/changes branch/gains a gate. Owner = Ian by default, watcher = Archivist, until Ian assigns it (the SnapDog pattern).
    • CHANGELOG.md: one dated line per day summarising the diff (repos moved, new folders), not a per-commit dump.
    • Decisions still need Ian's own words (or a bot reporting his yes in its chat, marked as such) — a scanner diff is evidence of work, never evidence of a decision.
    • LATEST-DIFF.md on the box is overwritten each deep run; dated manifests are kept for 14 days, then pruned.

Cost / noise tradeoffs

  • Dirty counts are the expensive and noisy part: SecureWatch alone has ~2,000 dirty files and gameengine ~900. Intraday scans skip them; daily dirty is reported only as deltas over +50 files or a repo going clean→dirty, with the known-huge repos baseline-muted.
  • The NAS is the slowest root by far: it is a mounted share, and a full git status pass over it runs many times slower than a local scan (the baseline NAS pass was still running when the three local scans had all finished). NAS therefore gets inventory-only (names + mtimes, no git — a full git pass over SMB was aborted at >13 min and a HEAD-only git pass at >9 min in the baseline, while inventory-only took ~4 s), weekly, and is treated purely as a backup-lag check; it is never on the intraday path and its git HEADs are reported unverified.
  • Known-routine commits (e.g. product-diary's daily posts) are expected motion: they are logged, not flagged. Flagging is reserved for untracked or feature-branch motion.
  • Four check-ins a day is the most that stays quiet. More frequent (hourly) buys little: commits are the unit of shipped work, and the daily refresh already catches mtime-only (non-git) changes.

Failure handling

  • Mini unreachable by both SSH routes: run the tier on the MBP, mark every number canonical-unverified, and retry the mini at the next tier slot. Do not declare the mini down from ListMachines.
  • SOCKS/SSH tooling broken on the box (as on the morning of 2026-10-19): that is a box fault, not a mini fault; record it as such for Warden.
  • One repo hangs or errors: the scan continues; the repo is listed with its error in the diff so the gap is visible.
  • NAS mount missing on the MBP: skip the NAS check, note it, move on; the NAS is a replica, never a blocker.

What this does not do

  • No project code is read or changed; git metadata + folder names only.
  • No commits, pushes, or syncs are triggered by tracking. Replication is the environment's own mechanism (canonical mini), not the scanner's.
  • Tracked ≠ approved: an active repo found by scan goes to OPEN-WORK as in-development/unverified until Ian or its owner confirms scope.
